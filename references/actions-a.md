# Original actions A: carry, throw, grow, exchange

Study of **all 16 registrations** in [scenes-p3.js](../examples/upstream/scenes-p3.js) (15) and [diffity-review.js](../examples/upstream/diffity-review.js) (1). Read the complete files, including their local prop helpers. This is an action vocabulary, not a claim that every original is ready for a Reel. Preserve the [original credit](../THIRD_PARTY_NOTICES.md) when adapting substantial code.

**Evidence:** **V** means selected action states were rendered and visually inspected in the linked sheet; **S** means source study only. Seven detailed sheets cover 60 states; they complement the broader atlas. Their exact times, reproduction commands, source fingerprints and motion-check reports are in [gallery-a](gallery-a/README.md). A still sheet establishes positions and visible changes, not smooth playback. Motion checks cover only the seven selected scenes, default play.

Neither source contains a backpack or a coffee-carrying/drinking action. The laptop, drone, document, block and cookie are genuine carrying examples; the visitors and robot are genuine companions. Do not invent a `backpack` or `coffee` option from these files. Those requested examples require evidence from other sources.

## Choose a physical action first

| Story need | Concrete choice and source | What makes it lively |
|---|---|---|
| Deliver something | [Receipt throw](#paws-cost-cli) **V** | Catch → turn → pull arm back → release → spinning flight → acknowledgement. |
| Bring something to share | [Laptop/drone visitors](#pmakersae) **V** | Enter carrying → lift to show → hover → group reaction → leave. |
| Transform input | [Feed and crank](#pyaml-sample) **V** | Carry paper → insert → turn handle → machine shakes → changed paper rises. |
| Add, then take back | [Stack blocks](#pdata-structures-in-js) **V** | Lift over stack → lower → release → stack settles → retrieve. |
| Build understanding in stages | [Growing plant](#pmongo-playground) **V** | Input → travelling signal → small growth → staggered branches → admiration. |
| Ask and receive | [Review exchange](#diffity-review) **V** | Attach request → flick message → wait → helper works → reply → approve. |
| Present a new example | [Hang and straighten](#pawesome-minimal-sites) **V** | Bend to collect → lift → hang crooked → tap straight → stand back. |
| Get past a barrier | [Card retry](#pnode-basic-auth) / [carry a cookie](#pnode-session-auth) **S** | Initial obstacle or exchange → changed object → gate/door responds. |

For an adraka/yudrika remake, **possible staging choices**, not religious claims: borrow the request–pause–reply rhythm for a question followed by an explanation; borrow carrying and presenting for a question brought into view; borrow lift/hang/straighten for revealing an explanatory example. A carried sealed parcel is a new adaptation, not a scene verified here. Keep any answer hidden until the approved narration permits it. Do not portray human effort or a machine as the source of revealed knowledge. Throwing is useful for delivery metaphors; it need not be applied to sacred text.

## What the prop code actually does

The figure draws in its own smaller, possibly mirrored coordinate space. A scene's fixed stage positions are a different space. [The figure implementation](../runtime/stick.js#L361-L452) adjusts unreachable hands and keeps the near arm away from the head, so a requested hand position is not necessarily the position actually drawn.

- **Attached to the actual hand:** p3's local `held(g, J, fn)` ([lines 55–57](../examples/upstream/scenes-p3.js#L55-L57)) runs `inWorld(g, J, () => fn(J.W(J.handF), J.W(J.handB)))`. Those are the drawn front/back hands in stage coordinates. The bundled equivalent is `R.held`, not a generic object attachment system. Call it within `fig(..., { held: ... })`; that callback runs before the near arm is drawn, leaving the grip visible.
- **Object path leads the hand:** the block (`blk`) and picture (`newF`) have explicit stage paths. Their `held` callbacks use `inWorld` to draw at those positions; their poses separately aim at the object with `lp(...)`. Merely putting a drawing in `held` does **not** attach it to a hand.
- **Released or machine-mounted object:** draw outside `held`, with an explicit path or pivot. Switch once from held drawing to free drawing, preserving its release position. The receipt uses hard-coded flight endpoints; the drone blends a sampled hand position toward a hovering position. Neither uses a physics engine.
- **Companion and worn styling:** `fig` accepts `ink`, `far`, `bot` and `hat` in these examples. The desk robot in makers is instead a separate `mkRobot` drawing. These are distinct implementations; there is no backpack attachment demonstrated here.

## Three changes the core skill should make next

1. **Require a varied action shortlist before scene design.** Offer carrying/presenting, lifting/placing, throwing/delivering, growth/transformation and a companion exchange where appropriate. For the chosen action, write preparation → contact → action/release → response → held result. Borrow the rhythm and physical cause, not product names or a compulsory prop library.
2. **Teach the three actual prop relationships above.** Include one hand-attached example, one object-led two-hand lift, and one held-to-free transfer. Verify the actual returned hand position, facing direction, release continuity and draw order. Clothing/backpacks and drinking need separately studied examples; do not manufacture helper names.
3. **Make reveal timing and negative findings part of example review.** Original idle states often contain the payoff; native reset can erase it. For each borrowed scene, inspect preparation/release/arrival/result and the intended cut, then check continuous motion and phone-size composition. Keep source-only, sampled visual evidence and checker results distinct. Passing motion checks do not certify prop clearance, story timing, smooth secondary motion or full parity.
